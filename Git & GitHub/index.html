Interview scenarios

Use a clear sequence: inspect first, protect the work, then change history only when it is safe.

Q1 · Wrong branch, correct work

Four commits landed on main by mistake. What now?

First, inspect the history and working tree. Confirm the commits are yours and that there are no uncommitted changes you could overwrite.

git status
git log --oneline --decorate -n 6

If the commits are local: create the feature branch at the current tip, then move main back to its previous position.

git switch -c feature/my-work
git switch main
git reset --hard HEAD~4

Why: the new branch preserves all four commits before main is moved.

If they were pushed: push the new branch first, then coordinate before rewriting main. On a shared branch, prefer a revert or a follow-up PR instead of a force-push.

Use cherry-pick when only specific, self-contained commits need to be copied to another branch.

Q2 · Merge conflict during a PR

How would you resolve a conflict without hiding the risk?

Update the feature branch with the target branch, resolve each conflict intentionally, run tests, and let the PR show the resulting diff.

git fetch origin
git switch feature/my-work
git merge origin/main
# edit conflicted files, then:
git add path/to/resolved-file
git commit
git push

Why: fetching first uses the latest remote state, while a tested merge commit makes the resolution explicit and reviewable.

Command playbook

Small command groups are easier to remember than one long cheat sheet.

Inspect safely

Understand where you are before changing anything.

git status
git branch -vv
git log --graph --oneline --all

Save work on a branch

Create a branch without changing the commit history.

git switch -c feature/name
git push -u origin feature/name

Copy one commit

Apply a specific commit to the current branch.

git cherry-pick <commit-sha>

Undo safely on shared history

Make a new commit that reverses an earlier one.

git revert <commit-sha>

Conflict checklist

Never mark a conflict resolved just to make Git continue.

1. Find every unresolved file

Run git status. Look for conflict markers: <<<<<<<<, =======, and >>>>>>>.

2. Decide the intended behavior

Read both versions and the surrounding code. Ask the PR author or domain owner when the correct behavior is not obvious.

3. Stage and verify

After editing, run the relevant tests and git diff --check, then stage only the files you actually resolved.

4. Explain the resolution

Tell reviewers what conflicted and why you chose the final version. A clean merge is not proof of a correct merge.

Strong interview answer “I inspect before rewriting history, preserve the work on a new ref, and avoid force-pushing shared branches. If the history is already public, I coordinate with the team and prefer a revert or a normal merge over silently changing commit IDs.”
